# 墨线任务矩阵（TASK-MATRIX）

- 版本：v2.1.0，依据 v2.1 施工契约第 2 节的文件集与第 5 节的七步流程
- 定位：八类任务在七个步骤上的 owner、输入、产物与通过条件。判级规则与角色边界见施工契约第 1、2 节与 `ROLES.md`，本文件只写落位。

## 0 读法与文件集

七步固定为受理、设计、架构、设计确认、实现与测试、变更完成确认、收口。每格四段，依次是 owner、输入、产物、通过条件。本版不设门禁编号，通过条件写在格内，设计确认只认一张需修正项清单。

两类变更分开写，文件集不同。产品视角在变更目录下写 product.md、design.md、frontend.md、backend.md、test.md 五份；技术视角不建 product.md 与 design.md，写 tech.md、涉及侧的前后端 spec 与 test.md。

表 0-1 两类变更的文件集

| 视角 | 必写文件 | 不建 | 首部冻结依据 |
|---|---|---|---|
| 产品视角 | product.md、design.md、frontend.md、backend.md、test.md | tech.md | 设计确认清单为空时的提交 |
| 技术视角 | tech.md、frontend.md 或 backend.md（涉及侧）、test.md | product.md、design.md | 设计确认清单为空时的提交 |

六份 spec 的节标题、首部八个字段、N/A 写法以施工契约第 2 节为准。模板名以 `templates/README.md` 为准，本文件只列产物文件名。

## 1 判级

判级在受理时一次完成，产品提出、主会话确认；技术视角由架构提出。判级写进 spec 首部与第 2 节，改判走重开一次判级，不在实现阶段改。

表 1-1 八类任务

| 类型 | 视角 | 发起角色 | 文件集 | 完成标准 |
|---|---|---|---|---|
| 新功能 | 产品视角 | 产品 | 五份 | 五份 spec 齐，测试全过，流程点台账全部已完成且证据路径可打开 |
| 界面调整 | 产品视角 | 产品 | 五份，backend.md 在允许节写 N/A | 同上，另加截图与几何观测 |
| 缺陷修复 | 产品视角 | 产品 | 五份 | 复现用例先失败后通过，相邻回归全过 |
| 重构 | 技术视角 | 架构 | tech.md、涉及侧 spec、test.md | 等价性标准逐条成立，测试全过 |
| 数据迁移 | 技术视角 | 架构 | 同上 | 演练通过，行数与抽样核对一致，回滚点可用 |
| 性能优化 | 技术视角 | 架构 | 同上 | 基线、目标与实测三值齐，p95 达标 |
| 安全修复 | 技术视角 | 架构 | 同上 | 复现用例通过，越权用例通过，结论单独写 |
| 纯文档 | 产品视角 | 产品 | 五份，design、frontend、backend 在允许节写 N/A | 引用与示例可跑，读者确认，流程点台账已完成 |

表 1-2 缺陷严重级别

| 级别 | 判定信号 | 处置要求 |
|---|---|---|
| 致命 | 数据丢失、不可恢复、核心链路全断 | 立即停线，先回滚再修，24 小时内出根因 |
| 严重 | 核心功能不可用，有绕行但代价高 | 当轮修完，补回归用例 |
| 一般 | 非核心功能异常，有可用绕行 | 排入当轮或下轮，写明计划 |
| 轻微 | 观感、文案、边界提示 | 可并入相邻改动，不单独发版 |

缺陷修复必须写严重级别与依据，以先复现为前提。安全修复另写受影响版本与入口、利用条件、修复与验证方式；重构另写等价性标准与回滚点。

表 1-3 三类任务族

| 任务族 | 归入类型 | 专属通过条件 |
|---|---|---|
| 发布交付 | 新功能或纯文档 | 版本号与变更记录一致，回滚点可用 |
| 流程机制设计 | 纯文档 | 规则编号连续，旧号不复用 |
| 演练与运行操作 | 数据迁移或安全修复 | 演练记录齐，异常路径有处置 |

主类型唯一，附加类型最多两个，与主类型同时写进首部。附加类型只补产物与通过条件，不改主类型决定的文件集。

三类任务族的专属通过条件由承担该任务的角色自证，项目经理只登记完成状态，不做复核。

三类项目管理任务不属于变更判级，不改变表 1-1 的八类任务与第 3、4 节两张矩阵；它们只更新流程点台账与任务分派清单，不建 spec，也不计入变更文件集。

表 1-4 项目管理任务

| 类型 | owner | 输入 | 产出 | 完成标志 |
|---|---|---|---|---|
| 项目拆分与派单 | 项目经理 | 变更受理记录、各 spec 首部 | 任务分派清单（派单卡）、流程点台账 | 每个点有 owner，状态为「未开始」；卡上任务号、父卡号、拆分人、目标、scope、验收标准、证据、禁止项、依赖卡、并行组十项齐，不设第二人栏 |
| 状态跟进与返工转派 | 项目经理 | 流程点台账、各角色状态回报 | 台账状态与 owner 更新 | 状态只取五值；owner 置「进行中」「已完成」，项目经理置「未开始」「阻塞」「已取消」并改 owner |
| 完成确认 | 项目经理 | 流程点台账、三类测试产物与覆盖率报告路径 | 验收报告、复盘报告 | 全部点已完成，证据路径可打开，三类测试全绿，两项覆盖率各 95%，验收报告与复盘报告已落盘；各角色自证，不设第二人签字 |

拆分粒度仍按 SCH-05 至 SCH-08 判定，项目经理不因角色新增获得跳过判定表的权力。

## 2 七步流程

七步的通用 owner、输入、产物与通过条件见表 2-1；表 3-1 与表 4-1 按任务类型细化，两者冲突时以矩阵为准。

表 2-1 七步

| 步骤 | owner | 输入 | 产物 | 通过条件 |
|---|---|---|---|---|
| 受理 | 产品；技术视角为架构 | 用户原话、issue、技术债条目 | spec 首部与第 1、2 节 | 变更号已登记，类型与视角已定，范围与断言可读 |
| 设计 | 设计 | product.md | design.md | 七节齐，首部登记 product.md 的 sha256 |
| 架构 | 架构 | product.md、design.md | frontend.md、backend.md | 两份 spec 齐，第 7 节规范已写 |
| 设计确认 | 设计或架构（自检） | 全部 spec | 需修正项清单 | 清单为空，清单空时的提交写入首部即冻结 |
| 实现与测试 | 前端、后端、测试 | 冻结的 spec | 代码、单元与集成测试、test.md 第 1 至 4 节 | 测试全过，两项覆盖率各不低于 95%，命令可复跑 |
| 变更完成确认 | 项目经理 | 流程点台账、三类测试产物与覆盖率报告路径 | 验收报告、复盘报告 | 全部点已完成，三类测试全过，两项覆盖率各 95%，证据路径可打开，验收报告与复盘报告已落盘；各角色自证，不设第二人签字 |
| 收口 | 项目经理 | 流程点台账、索引 | INDEX、TECH-DEBT、版本与变更记录 | 索引、记录与技术债清单一致 |

完成确认的产物就是验收报告与复盘报告，写完即收口。验收报告只引测试产物与覆盖率报告的路径，不转录数字与命令输出。

表 2-2 设计确认

| 项 | 要求 |
|---|---|
| 谁做 | 产品视角由设计 owner 自检，技术视角由架构 owner 自检 |
| 查什么 | spec 是否满足用户要求且内部自洽，变更部分是否符合规范 |
| 输出 | 一张需修正项清单，不列合规表，不做逐条规则核对 |
| 怎么冻结 | 作者按清单改，复评到清单为空，清单空时的提交写入各 spec 首部 |
| 开发后发现问题 | 退回设计阶段并记录，不在开发阶段打补丁 |

## 5 禁止清单

以下事项出现即不计入本次交付。

| 序号 | 禁止项 |
|---|---|
| 1 | 跳过判级直接开工，或开发中改判类型 |
| 2 | 冻结后自行改 spec 而不走设计确认 |
| 3 | 没有设计确认清单就开工，或清单未空就冻结 |
| 4 | 实现阶段改 spec 正文，或绕过架构现场加约定 |
| 5 | 项目经理判断技术方案，或由项目经理承担实现与技术复核 |
| 6 | 未跑测试就登记完成，或把未跑项写成通过 |
| 7 | 改 scope 之外的文件与模块 |
| 8 | 引入新技术债而不登记，或把问题留给下个变更 |
| 9 | 覆盖率用合计值代替单元与集成两项 |
| 10 | 验收报告写存量功能或复述规范清单 |
