## 前置定义

本册正文之前先固定三件事：全册只用这十个术语、只认这一组状态值、只认这七个角色。第 1 章至第 9 章的规则直接使用这些词，不再重新定义；术语出现第二个叫法、状态出现第二个写法、角色出现第八个名字时，按本节改写。

### 术语十条

| 术语 | 定义 |
|---|---|
| 流程点 | 一次工作中承载一类产物的最小单元，分需求、设计、架构、开发、测试五类，按链顺序排列并单独编号 |
| 需求点 | 流程点链的起点，写清要解决什么，其余点由它派生 |
| 设计点 | 承载界面、交互与视觉规格的流程点，输入是需求点与设计约束 |
| 架构点 | 承载技术方案、接口形状与冻结提交的流程点，输入是需求点与设计点 |
| 开发点 | 按冻结 spec 写代码与单元、集成测试的流程点，分前端与后端两条 |
| 测试点 | 跑全量测试、端到端与真机关键路径并留产物路径的流程点 |
| 冻结 | 设计确认清单为空后的提交把 spec 固定下来、之后修改重新提交并登记的动作 |
| 打回 | 完成确认不通过时把改动退回并记录期望与实测差异的动作 |
| 解冻 | 冻结后因范围或验收标准变化撤销冻结、重新进入草稿的动作 |
| 变更包 | 一次需求从受理到交付的全部角色 spec 与验收报告载体，关闭后归档不复用 |
### 状态两值

变更 spec 首部的状态只取 `草稿`、`已冻结` 两个值。冻结由设计确认清单为空后的提交决定，主会话把该提交写进各 spec 首部即冻结。状态不手写迁移，也不再用 `实现中`、`通过` 描述 spec；交付结果由验收报告的结论字段记录。

### 流程点状态五值

流程点的状态只取 `未开始`、`进行中`、`已完成`、`阻塞`、`已取消` 五个值，由该点的 owner 在产物落盘、证据路径可打开后置 `已完成`，项目经理把状态写进 `docs/process/FLOW-POINTS.md`。状态不靠逐点验收推进，也不设第二人复核。
### 七个角色与可写范围

七个角色各有一段可写范围，任意两份范围没有交集，一个文件只有一个角色可写；确认关系与越界处理由第 3 章的规则约束。

产品写 `product.md`，负责用户原话、目标、非目标、假设与代价、验收层级、REQ 与 AC；不写设计、前后端、测试 spec、代码与验收报告。

设计写 `design.md`，负责目标与原则、信息架构与流程、界面与交互规格、状态与异常、设计令牌；不写代码、前后端与测试 spec。

架构写 `tech.md`、`frontend.md`、`backend.md`，技术视角由架构发起；架构登记输入哈希与冻结时点，不写代码、测试代码与验收报告。

前端写前端代码、单元与集成测试，不写 spec 正文、验收报告、复盘与后端代码。

后端写后端代码、单元与集成测试，不写 spec 正文、验收报告、复盘与前端代码。

测试写 `test.md`、端到端与真机清单及结果、端到端测试代码、两项覆盖率结果，不写产品代码、spec 正文与验收报告。

项目经理维护 `docs/process/FLOW-POINTS.md`，收口阶段写 `docs/testing/ACCEPT-<CHG-ID>-<YYYYMMDD>.md`，可代写 `docs/plan/RETRO-<YYYYMMDD>-<REQ-ID>.md`；负责拆分任务、派单、跟进状态与转发返工，不写 spec、代码与测试，不做第二人复核，不给自己写的报告改结论。

## 第 1 章 目的、范围与自证

本章决定一项工作是否进入本册，以及本册与其它流程文件冲突时按哪一份执行。范围判定发生在受理之前，判为不适用的工作不建变更包，判为适用而没有变更记录的工作不计入交付。本章的规则对所有后续章节生效，后续章节不另立适用范围。

### MXV2-1-01 纳入范围的工作必须建立变更包

- 规则：在本仓库内产生受版本管理的文件改动、用户可观察的行为变化、存量数据结构变化，或结论需要他人复算的工作，按本册执行并建立变更包。
- 验收标准：改动所在的提交能指到一个 `specs/changes/<CHG-ID>/` 目录，目录内有该类型要求的角色 spec；四项纳入条件在 `product.md` 第 2 节或 `tech.md` 第 2 节逐条写明并给出结论。
- 执行：`ai-review:按本条验收标准逐项核对并留证据`；谁判：本条 owner；误放行：验收标准不满足仍被通过；误拦截：证据齐全仍被要求重做。
- 层级：L1
- 依据：MX-1-01、MX-1-02
- 适用：任何改动落盘之前与合入之前各查一次。

### MXV2-1-02 五类工作不纳入本册

- 规则：调研、只读排查、一次性命令、环境安装与清理、纯对话讨论五类工作不纳入本册，判定时逐条对照表 1-1，不按工作量或耗时推断。
- 验收标准：五类工作各能在表 1-1 找到一行，行的判定依据写明为什么没有仓库文件改动、没有行为变化或没有人需要复算。
- 执行：`ai-review:五类排除逐条对照表 1-1，排除理由指向具体工作`；谁判：本条 owner；误放行：该建包的工作被当作调研跳过，改动落地后没有依据；误拦截：只读排查被判为纳入，为一次查证建包。
- 层级：L1
- 依据：MX-1-03
- 适用：受理时；同一项工作后来产生文件改动时重判一次。

表 1-1 适用范围

| 工作 | 是否纳入 | 判定依据 | 落地方式 |
|---|---|---|---|
| 新增或修改用户可观察的能力、页面、接口与字段 | 纳入 | 交付后行为变化可被他人复算 | 变更包、派单消息、证据 |
| 只改文档且文档进入仓库被引用 | 纳入 | 产生受版本管理的文件改动 | 轻量变更包、文档校验门 |
| 改存量数据或迁移结构 | 纳入 | 需要迁移、回填、双写或回滚 | 变更包、迁移演练 |
| 随变更包发生的发布与部署动作 | 纳入 | 改变运行环境且随本次交付发生 | 变更包、发布检查单 |
| 调研与只读排查 | 不纳入 | 不产生仓库文件改动 | 结论写入现有记录或旁路清单 |
| 一次性脚本与命令 | 不纳入 | 用完即弃且不入仓 | 执行记录留在会话 |
| 环境安装、清理、进程启停 | 不纳入 | 不改变仓库内容 | 运维日志 |
| 纯对话讨论与口头答复 | 不纳入 | 没有落盘产物 | 无 |

### MXV2-1-03 判为不纳入的工作不建包，产生改动时补包

- 规则：判为不纳入的工作不建变更包、不写 spec、不占编号；同一项工作后来产生仓库文件改动时，在改动落盘前补建变更包，并按事故登记补记。
- 验收标准：排除记录里写明了判定依据与本条 owner；后来产生改动的，改动落盘时间早于变更包建立时间的，有一条 `FAIL-<CHG-ID>-<NN>` 登记。
- 执行：`ai-review:排除记录有依据，补包时间与改动时间可对照`；谁判：本条 owner；误放行：先改代码后补包，补记被省略，编号与时间线失真；误拦截：把一次只读查证要求补包。
- 层级：L1
- 依据：MX-1-04
- 适用：受理时判为不纳入之后，以及该工作再次产生改动时。

## 第 2 章 术语、编号与状态

### MXV2-2-01 术语以十条为准，一概念一词

- 规则：术语以前置定义的十条为准，同一概念全册只用一个词；出现同义词、近义词或英文别称时按十条改写，不新增第十一个术语。
- 验收标准：全册检索同一概念只有一种写法；新增术语的提案能指到十条中的一条并说明为何不能复用；同义词出现处已改写。
- 执行：`ai-review:全册检索同一概念只有一种写法，新增术语的提案能指到十条中的一条并说明为何不能复用，同义词出现处已改写`；谁判：架构；误放行：缺项内容进入评审或入库；误拦截：合规写法被要求重写。
- 层级：L1
- 依据：MX-3-01
- 适用：写任何条文之前；评审时全文扫描一次。

### MXV2-2-02 编号在创建时分配并写入文件首部

- 验收标准：每个对象文件首部有编号行；编号与表 2-1 的格式一致；追溯矩阵里的编号都能在文件首部找到。

- 层级：L2

- 适用：对象创建时；收口核对时。

### MXV2-2-03 编号不复用，取消留空号

- 规则：编号一经分配不再复用；对象取消后保留空号，并在追溯矩阵记“已取消”，空号不得转给同类新对象。
- 验收标准：同一编号在追溯矩阵只出现一次；取消项有“已取消”标记与取消日期；新对象的编号大于同类已用最大号；验收报告 中同一起点编号只出现一次。

- 层级：L2
- 依据：MX-3-03
- 适用：任何编号分配与取消之后。

### MXV2-2-07 AC 判定只取两值

- 规则：AC 判定只取 `pass`、`fail` 两值；验收标准执行且满足记 `pass`，验收标准执行且不满足或未执行记 `fail`，未执行的另写原因与解除条件。
- 验收标准：验收报告第 2 节每条 AC 的取值属于两值；`fail` 有原因与解除条件；没有第三值。
- 执行：`ai-review:逐条核对验收报告第 2 节的 AC 取值只有 pass 与 fail，fail 有原因与解除条件`；谁判：本条 owner；误放行：用“基本通过”代替 fail；误拦截：证据齐全的 pass 被要求补写原因。
- 层级：L1
- 依据：MX-2-07、CHG-FW-003 裁决
- 适用：每条 AC 判定时。

### MXV2-2-08 两值判定按固定顺序

- 规则：判定顺序固定为：先看本轮有没有执行记录，有执行记录再比对验收标准，满足记 `pass`，不满足记 `fail`；没有执行记录直接记 `fail` 并写未执行原因。
- 验收标准：每条判定能指到本轮执行记录；`pass` 之前有命令与退出码；没有执行记录的项一律为 `fail`。
- 执行：`ai-review:核对每条判定的执行记录，确认 pass 之前有命令与退出码，无执行记录的项为 fail`；谁判：本条 owner；误放行：跳过执行直接判 pass；误拦截：已执行且满足仍被判 fail。
- 层级：L1
- 依据：MX-2-08、CHG-FW-003 裁决
- 适用：判定每条 AC 时。

### MXV2-2-09 fail 必须写原因与解除条件

- 规则：判定为 `fail` 时必须在同一行写原因、解除条件、责任人与期限四项，`pass` 不写；原因写失败现象或未执行依据，不写“基本”“待补”这类词。
- 验收标准：每一条 `fail` 的四项非空；责任人是七个角色之一；期限写到日期；`pass` 行不出现这四项。
- 执行：`ai-review:逐条核对 fail 行的原因、解除条件、责任人与期限四项，pass 行不写`；谁判：本条 owner；误放行：fail 只写“待修”没有责任人与期限；误拦截：pass 行被要求补原因。
- 层级：L1
- 依据：MX-2-09、CHG-FW-003 裁决
- 适用：写非通过判定时。

### MXV2-2-10 未执行项写四段，不设码表

- 规则：未执行的 AC 在同一行写未执行原因、解除条件、责任人与期限四段，不设独立码表；第 7 章与第 8 章只引用本条，不另立码表。
- 验收标准：未执行项四段齐全；正文没有码表编号；第 7、8 章没有独立的码表。
- 执行：`ai-review:核对未执行项四段与正文无码表`；谁判：本条 owner；误放行：只写“环境问题”没有解除条件；误拦截：四段齐全仍被要求补码表。
- 层级：L1
- 依据：MX-2-10、CHG-FW-003 裁决
- 适用：写未执行项时。

### MXV2-2-11 状态只有草稿与已冻结

- 规则：变更 spec 首部的状态只取 `草稿`、`已冻结` 两值；冻结由设计确认清单为空后的提交决定，主会话把该提交写进首部即冻结；不设 `实现中`、`通过` 状态。
- 验收标准：首部状态字段属于两值；冻结时点的提交为 7 至 40 位十六进制且与设计确认清单清空时的提交一致；交付结果另写验收报告，不写进状态字段。
- 执行：`ai-review:核对首部状态两值与冻结时点提交的一致性`；谁判：架构；误放行：用“实现中”描述 spec 状态；误拦截：冻结时点提交为空但清单未清空仍被要求填写。
- 层级：L1
- 依据：MX-2-11、CHG-FW-003 裁决
- 适用：写 spec 首部与冻结时。

### MXV2-2-12 状态由产物推导，不设迁移动作

- 规则：状态由 spec 首部与设计确认清单推导，不设冻结、开工、通过、打回、解冻的迁移动作；设计确认清单为空即冻结，完成确认结论由验收报告记录；原冻结判定 已删除，4-19、8-12、9-11 不引用。
- 验收标准：正文没有状态迁移表；冻结能指到清单为空的提交；完成确认结论能在验收报告第 4 节找到。
- 执行：`ai-review:核对正文无迁移表，冻结与完成确认结论各有落点`；谁判：架构；误放行：按旧迁移表改状态；误拦截：冻结已写仍被要求补迁移记录。
- 层级：L1
- 依据：MX-2-12、CHG-FW-003 裁决
- 适用：任何冻结与交付结论判定时。

### MXV2-2-13 五个禁用词出现即按未判定

- 规则：禁用词限于“基本完成”“差不多通过”“应该可以”“暂时通过”“原则通过”五类，出现任一即按未判定处理，结论记 `fail`。

## 第 3 章 角色与授权

本章只规定角色怎么引用、确认怎么分、越界怎么处理，不复制角色卡正文。角色名称、输入、产出与不写什么以前置定义那一节为准，`docs/framework/ROLES.md` 维护同一套角色卡。自证是本章的核心约束：每个角色对自己产物负责，项目经理只落台账与汇总报告，不替 owner 下结论。

### MXV2-3-01 每个产出物只有一个 owner

- 规则：七个角色按前置定义那一节取值，每个产出物只有一个 owner 角色，owner 写在文件首部或派单消息上；两个角色同时署名时以派单消息登记的 owner 为准，其余署名者按评审记。
- 验收标准：每个产出物文件首部或所属派单消息有唯一的 owner 角色名；同一产出物不出现两行 owner；评审记录另列，不写成第二 owner。
- 执行：`ai-review:按本条验收标准逐项核对并留证据`；谁判：本条 owner；误放行：验收标准不满足仍被通过；误拦截：证据齐全仍被要求重做。
- 层级：L1
- 依据：MX-2-01、MX-2-02
- 适用：任何产出物建立与移交时。

### MXV2-3-02 owner 自证，不设他人复核

- 规则：每个角色对自己产物自证，产物落盘且证据路径可打开即置 `已完成`；不设第二人复核，不要求实现者以外的人签字；项目经理只把状态写进 `docs/process/FLOW-POINTS.md`，不改写 owner 的结论。
- 验收标准：状态由该点 owner 置；证据路径可打开；没有第二人复核记录；项目经理未改写结论。
- 执行：`ai-review:核对台账状态、证据路径与结论归属`；谁判：本条 owner；误放行：项目经理替 owner 下结论；误拦截：项目经理汇总被误判为复核。
- 层级：L1
- 依据：MX-3-02、CHG-FW-003 裁决
- 适用：每个流程点完成时。
### MXV2-3-03 用户只看前端效果与异常出口

- 规则：用户只看前端效果与异常出口裁决，不占七个角色中的任何一个；用户意见由产品落盘后才算记录，不由其它角色代述。
- 验收标准：用户意见有产品落盘记录；没有代述；前端效果有用户确认记录。
- 执行：`ai-review:用户意见落盘正确，前端效果有确认记录`；谁判：产品；误放行：把口头意见当记录；误拦截：产品按用户意见落盘被判代述。
- 层级：L1
- 依据：MX-3-03、CHG-FW-003 裁决
- 适用：用户看效果与异常出口裁决时。
### MXV2-3-04 一人多角色取更窄的可写范围

- 规则：一人兼多角色时以更窄的可写范围为准，同一份文件的连续修订只由同一角色完成；判定权与执行权落在同一人时，判定交给独立角色。
- 验收标准：兼任记录写明取哪个角色的可写范围；同一文件的多轮修订记录指向同一角色；判定记录的执行人不等于本条 owner。
- 执行：`ai-review:兼任取窄有记录，判定权与执行权分离`；谁判：本条 owner；误放行：兼任者用宽角色的范围改窄角色的文件，越界不被发现；误拦截：把同一角色的连续修订判为跨角色。
- 层级：L1
- 依据：MX-2-05
- 适用：一人承担两个及以上角色时。

### MXV2-3-05 角色缺席由主会话指派代理

- 规则：角色缺席时由主会话指派代理，代理范围与期限写进派单消息；代理只补该角色的产物与自证，代理自己实现的产物仍由代理自证。
- 验收标准：派单消息有代理角色名、代理范围与到期日三项；代理期间的确认人不等于实现 owner。
- 执行：`ai-review:代理三项齐全，自证归属正确`；谁判：本条 owner；误放行：代理把自己的实现签掉；误拦截：同一角色内部临时顶班被判为代理。
- 层级：L2
- 依据：MX-3-07、CHG-FW-003 裁决
- 适用：角色缺席时。

### MXV2-3-06 唯一 owner 缺失时停在当前阶段

- 规则：一个产出物找不到唯一 owner 时变更包停在当前阶段，补登记角色分配后才继续；补登记写进派单消息或检查点，只留在对话里的分工视为未分配。
- 验收标准：阶段推进时间晚于 owner 补登记时间；补登记有角色名、产出物与时间三项；对话记录不作为分配依据。
- 执行：`ai-review:停在当前阶段且补登记先于推进`；谁判：本条 owner；误放行：无人负责的产出物往下走；误拦截：已在派单消息登记仍要求再登记。
- 层级：L2
- 依据：MX-3-08、CHG-FW-003 裁决
- 适用：产出物没有唯一 owner 时。

### MXV2-3-07 判定冲突按职责归属裁决

- 规则：两个角色对同一判定给出不同结论时，按 `docs/framework/ROLES.md` 的职责归属裁决；仍不一致时按口径冲突登记异常，不按成本最低或进度最快的一方裁定。
- 验收标准：冲突记录有双方结论、职责归属依据与裁决结论三项；裁决依据能指到 ROLES.md 的具体职责行；登记有异常编号。

## 第 5 章 任务类型与规格分层

本章把任务类型、判级手续与规格载体写成一套可对照的规则。类型只有八类，判级在受理阶段一次完成；规格按角色分文件，接口与数据契约写前后端 spec 第 3 节，规范要求写第 7 节，两者都不另建表格或编号。

### MXV2-5-01 任务类型只取八类

- 规则：任务类型只取新功能、界面调整、缺陷修复、重构、数据迁移、性能优化、安全修复、纯文档八类，不设第九类；各类型的分阶段验收标准、模板与门禁以 `docs/framework/TASK-MATRIX.md` 为准，本章只写判级顺序、主附加类型与严重级别，不复制矩阵表。
- 验收标准：变更包首部的主类型取值属于八类；引用矩阵处写章节号而非复制内容；矩阵与本册冲突时二十四小时内有回写登记。
- 执行：`ai-review:变更包首部的主类型取值属于八类，引用矩阵处写章节号而非复制内容，矩阵与本册冲突时二十四小时内有回写登记`；谁判：架构；误放行：契约与设计缺口流入实现；误拦截：合规契约被要求返工。
- 层级：L1
- 依据：MX-4-01、MX-4-18
- 适用：受理判级时；矩阵修订后。

### MXV2-5-02 判级在受理阶段一次完成

- 规则：判级在受理阶段一次完成，结论写入变更包首部的主类型、附加类型、非目标、影响面与判级理由五个字段，五个字段各有值时判级才算完成，不允许留到契约阶段补。
- 验收标准：首部五个字段齐全；判级时间早于 spec 冻结时间；判级理由引用矩阵的判别信号原句，没有“感觉像”“应该属于”这类说法。
- 执行：`ai-review:按本条验收标准逐项核对并留证据`；谁判：本条 owner；误放行：验收标准不满足仍被通过；误拦截：证据齐全仍被要求重做。
- 层级：L1
- 依据：MX-4-02、MX-4-16
- 适用：受理任何任务时。

### MXV2-5-03 判级按五步固定顺序

- 规则：判级按表 5-1 的固定顺序进行：先看交付物，再看安全，再看数据，再看行为，最后看指标；前一步成立即停止，顺序不因任务大小调整。
- 验收标准：判级记录写明停在第几步与成立条件；步骤号与表 5-1 一致；没有跳步后回填的结论。
- 执行：`ai-review:判级记录写明停在第几步与成立条件，步骤号与表 5-1 一致，没有跳步后回填的结论`；谁判：架构；误放行：契约与设计缺口流入实现；误拦截：合规契约被要求返工。
- 层级：L1
- 依据：MX-4-03、MX-4-04、MX-4-05、MX-4-06、MX-4-07、MX-4-08
- 适用：受理判级时。

表 5-1 判级步骤

| 步 | 看什么 | 成立时结论 | 不成立时 |
|---|---|---|---|
| 1 | 只改文档，不含代码、配置、数据与界面改动 | 纯文档 | 进第 2 步 |
| 2 | 存在已识别漏洞且修复目的是消除可利用性 | 安全修复 | 进第 3 步 |
| 3 | 改变存量数据的结构、位置或语义 | 数据迁移；只新增可回滚表或字段时记附加类型并继续 | 进第 4 步 |
| 4 | 行为不变，或变化属于纠正、界面、新增能力 | 重构、缺陷修复、界面调整、新功能之一 | 进第 5 步 |
| 5 | 行为不变且以指标改善为目标 | 性能优化 | 停在受理阶段，补判级规则 |

### MXV2-5-04 主类型唯一，附加类型最多两个

- 规则：每个任务只写一个主类型，附加类型最多两个；主类型决定完成确认出口与阶段必做集，附加类型只叠加特有门禁与证据项；涉及安全漏洞以安全修复为主类型，涉及存量数据改写、删除或搬迁以数据迁移为主类型，其余按交付目标取主类型。
- 验收标准：主类型恰有一个；附加类型不超过两个；附加类型达到三个及以上时有拆分记录；主类型与特有门禁项对得上。
- 执行：`ai-review:主类型恰有一个，附加类型不超过两个，附加类型达到三个及以上时有拆分记录，主类型与特有门禁项对得上`；谁判：架构；误放行：契约与设计缺口流入实现；误拦截：合规契约被要求返工。
- 层级：L1
- 依据：MX-4-09、MX-4-10、MX-4-11

## 第 6 章 规则格式与判定

本章规定一条规则长什么样、怎么判、写不出验收标准时怎么处理。规则是可执行条款，不是口号：每条规则一个编号、一句陈述、一个可观察的验收标准，验收标准与执行手段分开写，判定点挂到门禁上。本章的规则卡格式适用于全书，包括附录 D 的未判定条目。

### MXV2-6-01 每条规则六字段齐全

- 规则：每条规则卡必须同时有编号、陈述、验收标准、执行手段、层级与来源出处六个字段，六个字段各占一行，缺任一个字段时该规则视为未成立，不得写入正文。
- 验收标准：规则卡字段数等于六；编号与标题行一致；验收标准行不是“见上文”“按规范执行”这类空指向；来源出处可解析到 SOURCES.md 或旧规则号。
- 执行：`ai-review:按本条验收标准逐项核对并留证据`；谁判：本条 owner；误放行：验收标准不满足仍被通过；误拦截：证据齐全仍被要求重做。

- 依据：S-025、S-026
- 适用：新增或修订任意规则时。

### MXV2-6-04 一条规则只做一件事

- 规则：一条规则只约束一个可独立判定的对象，陈述写一句祈使句；同一对象的方法、例外与后果写在同一句里用分号隔开，不把两件事并进一条规则。
- 验收标准：陈述行只有一句且以动词开头；规则内出现的对象不超过一个；判断需要两个互不相关的检查时已拆成两条。
- 执行：`ai-review:逐条读陈述，检查是否一句话一件事、是否以动词开头、是否夹带第二件事`；谁判：本条 owner；误放行：把“门禁失败要停工并登记”这类两件事写成一条，判定点分散；误拦截：把带条件从句的一句话判成两件事。
- 层级：L2
- 依据：S-025、S-035
- 适用：起草与修订规则陈述时。

### MXV2-6-05 验收标准写可观察条件

- 规则：验收标准只写能被第二个人复现的观察结果，写清比较符、数值、单位、文件路径或取值集合；不写“合理”“充分”“应当明确”这类需要再解释的说法。
- 验收标准：验收标准行含比较符、数值或路径至少一项；不含形容词式判断；同一验收标准两次执行结论一致。
- 执行：`ai-review:验收标准行含比较符、数值或路径至少一项，不含形容词式判断，同一验收标准两次执行结论一致`；谁判：架构；误放行：缺项内容进入评审或入库；误拦截：合规写法被要求重写。
- 层级：L2
- 依据：S-025、S-036
- 适用：写验收标准行时。

### MXV2-6-06 验收标准与执行手段分开写

- 规则：验收标准写“什么算成立”，执行手段写“用哪条命令或哪次人工判定去查”，两者各占一行，不互相替代；执行手段里不重复验收标准内容，验收标准里不写命令参数。
- 验收标准：每张卡同时有验收标准行与执行手段行；执行手段行的内容不是验收标准的复述；命令参数只出现在执行手段行。
- 执行：`ai-review:对照验收标准行与执行手段行，确认验收标准不含命令、执行手段不含验收标准复述`；谁判：本条 owner；误放行：把命令退出码写进验收标准，执行手段反而空着，无法复跑；误拦截：验收标准引用契约取值、执行手段引用脚本，两者本就分工明确。

### MXV2-6-07 script 类执行手段写命令与期望退出码

- 验收标准：命令含脚本路径、`--rule` 与编号；有“期望退出码 0”的字样；脚本不存在时证据里有人工核对记录。

### MXV2-9-01 Git 回滚四类触发，命令按情形区分

- 规则：Git 回滚的触发有四类：完成确认失败且缺陷定位不清或修复需要改契约、单个文件改坏且改动尚未提交、已推送的提交需要撤销、运行时开关或新旧模型双跑需要关闭并回退；未提交的单文件改动用 `git restore -- <文件>`，本地未推送的提交用 `git reset --soft <回滚点>`，已推送的提交用 `git revert <提交号>`；回滚后重跑原绿项断言与一次整线复跑，命令、退出码与输出写进证据文件；登记在 24 小时内完成，禁止 `git reset --hard`、`git clean -fdx`、`git push --force` 与删除未跟踪文件。
- 验收标准：触发类型有记录；命令与情形对应；回滚后复验输出存在；禁止命令未出现。
