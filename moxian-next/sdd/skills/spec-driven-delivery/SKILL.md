# 按规格完成一次变更

从已有工单、复现或契约差异开始。先读受影响的实现、消费者和项目指令。工作范围清楚时连续完成下面的活动。只为会改变交付的未决事项找有决定权的人。

1. **明确结果。** 从工单追到本次改动的公开入口、项目契约原文和实际调用方。Markdown 工程可用 `sdd contract '路径#条款编号'` 取完整章节。沿这条路径核对哪些成功结果、失败或恢复、合法边界和旧行为已被承诺。用现有测试的具体断言对照；缺失的条件直接补在工程测试里。产品文字与旧消费者有冲突时，按项目已作出的决定处理，影响实现的未决项交有决定权的人。工单、契约或测试中已有的结论直接引用。
2. **确定共享约定。** 找出生产方和使用方需要一致的字段、错误和可见结果。跨层变更至少沿真实入口验证两端对同一数据的解释。需要参考时，`sdd topics backend qa` 列出对应角色的条目标题，`sdd topic 5.2 7.1` 读取选中的完整条目。一个执行者可以承担多个角色。
3. **实现并验证。** 缺陷优先复现旧行为。先跑能区分对错的最近一层，按实际差异带上受影响的消费者。项目已有 affected、测试命令或 CI 时直接使用。共享契约、迁移、构建配置、无法确定的依赖要扩大到相应消费者或全量；最终候选继续遵守项目合并必查项。缺少原生选测且已有维护好的项目映射时，`sdd impact --policy ... --base ... --run` 可直接运行这些检查。检查进程状态、必查用例命中及适用的清理结果；Go 新运行需要点名时用 `sdd test-go`。已有同一候选的有效工程结果直接复用。
4. **核对并交付。** 对照承诺、当前修订和原始结果。已有检查足以验收时，在原工单或 PR 给出结果引用即可。缺少的行为、未验证环境及失败保留其实际状态。需要独立批准时取得目标修订上有权者的决定。交付、部署和生产观测分别按用户授权及工程要求执行。

新事实改变约定时，只撤销受影响的结论。原生缓存按工程的输入与环境使用。超时或中断后先确认旧运行和外部资源的实际状态，能够确定重放安全时再恢复。
